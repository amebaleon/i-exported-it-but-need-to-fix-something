# Windows 실행 보고서

## 재현 환경

2026-11-10, Windows 11 Pro 10.0.26200 x64, Intel Core i7-1260P, Rust 1.99.1 MSVC release 빌드, FFmpeg/FFprobe 9.0.2 Gyan shared GPL 빌드, Node.js 25.1.0. Premiere 설치·Adobe 구독·GPU 인코딩 없이 실행했다.

```powershell
cargo test --release --locked
cargo test --release --locked --test benchmark -- --ignored --nocapture
node --test premiere/adapter.test.js
cargo fmt --check
cargo clippy --all-targets --locked -- -D warnings
```

기본 Rust 테스트 19개, 별도 Rust 벤치마크 1개, Node 테스트 1개가 통과했다. rustfmt와 Clippy 경고 검사도 통과했다. 개발 중 원본의 CRF가 23인 호환성 사례에서 PPS 불일치가 발견되었다. 원본 x264 SEI에서 얻을 수 있는 CRF를 사용하고 최종 avcC 일치 검사를 유지한 뒤 해당 테스트가 통과했다.

미디어 회귀 테스트는 192×108, 24 fps, 720프레임의 움직이는 testsrc2에 48 kHz AAC를 넣고, 색상이 반전된 120프레임을 교체한다. 모든 출력에 엄격한 디코드 검사를 수행하고, 패킷 수·표시 순서·PTS·DTS·duration·오디오 priming을 확인한다. 원본·교체본을 복사한 영역은 압축 SHA-256과 디코딩 frame MD5를 대조한다. 손실 재인코딩 영역은 모든 프레임을 기대 영상과 32×18 휘도로 비교한다(MSE < 12). AAC는 디코딩 PCM도 일치한다.

별도로 PATH를 FFmpeg bin과 Windows 시스템 폴더로 제한하고 Python, Node, Cargo 명령이 탐색되지 않는 것을 확인했다. 이 환경에서 이미 빌드된 실행 파일로 분수 FPS의 복수 구간 교체 테스트를 다시 통과했다.

## 720p 처리 시간 및 I/O

1280×720, H.264 High yuv420p, libx264 medium CRF 18, B-frame, 고정 48프레임 GOP, 24 fps, 30초. 원본에는 48 kHz AAC가 있고, 교체 영상은 5초 무음이다. 측정 전에 두 입력을 생성했다. 편집기에서 교체 영상 자체를 만드는 시간은 양쪽에서 제외했다.

`patch`는 분석·인코딩·MP4 작성·전체 검증·파일 게시까지 측정했다. 전체 재인코딩은 FFmpeg overlay로 같은 11–16초 수정을 적용하고 720프레임을 libx264 medium CRF 18로 인코딩하며 원본 오디오를 복사한다. 전체 재인코딩 측정은 파일 작성 완료 시 끝난다. 두 결과의 프레임 비교는 측정 후에 수행한다. 실행 순서는 회차별로 교대했고 OS 파일 캐시는 비우지 않았다.

| 회차 | 부분 패치 (ms) | 전체 재인코딩 (ms) | 부분 읽기 / 쓰기 (B) | 전체 읽기 / 쓰기 (B) |
|---:|---:|---:|---:|---:|
| 1 | 1,367 | 4,451 | 79,889,324 / 18,692,880 | 18,749,093 / 15,651,591 |
| 2 | 1,333 | 4,424 | 79,889,324 / 18,692,880 | 18,749,093 / 15,651,591 |
| 3 | 1,375 | 4,344 | 79,889,324 / 18,692,880 | 18,749,093 / 15,651,591 |

중앙값은 부분 **1.367초**, 전체 **4.424초**, 약 **3.24배**다. Rust 프로세스 및 FFmpeg/FFprobe 자식 전체의 Windows Job Object 전송량을 읽었다. 이 값에는 캐시와 파이프 I/O도 포함된다. 물리 SSD에서 실제 전송된 바이트는 이번 측정으로 구분할 수 없다. 패치의 여러 검증 패스 때문에 읽기량은 전체 인코딩보다 많았다.

| 출력 시각 | 프레임 구간 (끝 제외) | 처리 |
|---|---|---|
| 0–10초 | [0, 240) | 원본 패킷 240개 복사 |
| 10–11초 | [240, 264) | 끊긴 원본 GOP의 24프레임 재인코딩 |
| 11–16초 | [264, 384) | 교체 MP4의 압축 패킷 120개 복사 |
| 16–30초 | [384, 720) | 원본 패킷 336개 복사 |

720프레임 중 원본 패킷 576개와 교체 패킷 120개를 검증했다. 인코딩 조각은 550,597 B, 최종 mdat 페이로드는 15,970,828 B, 최종 MP4는 15,998,664 B였다. 전체 재인코딩 결과는 15,651,587 B였다. 1회차 부분 패치 내부 계측은 분석 239 ms, 인코딩 조각 준비 372 ms, MP4 작성 63 ms, 출력 검증 687 ms였다.

정렬된 30000/1001 fps 별도 테스트에서는 192프레임 중 원본 96개와 교체 96개를 복사해 **재인코딩 0프레임**으로 완료했다. 다른 파라미터 세트를 가진 교체본 테스트에서는 96프레임을 재인코딩했다. 입력 구조와 호환성이 달라지면 인코딩 프레임 수와 속도도 달라진다.

## 남은 검증과 다음 개발 순서

1. Premiere 실기에서 `.epr` 첫 내보내기, 완료·취소 시점, 폴더 권한과 캐시를 확인한다. 실제 소스·효과·자막을 빠짐없이 수집할 수 있는 시퀀스부터 구간 렌더와 두 버튼의 왕복을 검증한다.
2. 긴 실제 내보내기에서 패킷 인덱스 캐시, FFprobe 처리, 전체 출력 디코딩의 비용을 측정한다. 이번 720p 측정에서 검증이 가장 긴 단계였다. CLI와 Rust 파일 작성 경로를 기준선으로 유지한다.
3. 실제 Premiere H.264 프리셋별 SPS/PPS와 MP4 샘플 테이블 호환성 자료를 확보한 뒤 지원 범위를 넓힌다. 현재 HEVC, VFR, 오디오 편집, 길이 변경, 전환·중첩 시퀀스 자동 추적은 후속 범위다.
